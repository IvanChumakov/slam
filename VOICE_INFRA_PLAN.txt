======================================================================
1. ЦЕЛЬ НАШЕЙ РАБОТЫ
======================================================================

Поднять и проверить голосовую инфраструктуру для Telegram Voice MVP.

Итоговая цепочка должна работать так:

Telegram join-ссылка
        -> web-клиент
        -> backend выдаёт LiveKit JWT
        -> LiveKit принимает участников
        -> участники слышат друг друга через WebRTC

Главный критерий успеха:

Два пользователя из разных сетей открывают одну голосовую комнату в
обычных браузерах, слышат друг друга и не используют VPN.

4. ПРИНЯТЫЕ ТЕХНИЧЕСКИЕ РЕШЕНИЯ
======================================================================

1. Используем self-hosted LiveKit Server.
2. Локальная среда запускается через Docker Compose.
3. Staging размещается на одной Linux VM с публичным IPv4.
4. Для staging используем Docker Compose, Caddy и Redis.
5. Сначала используем встроенный TURN LiveKit.
6. Отдельный coturn добавляем только при подтверждённой проблеме
   встроенного TURN.
7. Основной публичный адрес: wss://rtc.example.ru.
8. Для TURN желательно использовать отдельный домен turn.example.ru.
9. Для независимых проверок используем LiveKit CLI и официальный
   совместимый тестовый клиент LiveKit Meet.
10. API key, API secret, сертификаты и реальные .env не коммитим.
11. Docker-образы фиксируем по версии, не используем latest без причины.
12. Сначала доказываем локальную передачу голоса, затем выполняем staging.

Если какое-либо решение меняется, изменение нужно записать в раздел
"Журнал решений" в конце этого файла.

13. ЭТАП 7 — FIREWALL, TURN И FALLBACK
======================================================================

Базовые порты, которые нужно согласовать с итоговым livekit.yaml:

- TCP 80: выпуск/обновление TLS-сертификатов.
- TCP 443: HTTPS/WSS и TURN/TLS.
- TCP 7881: WebRTC over TCP fallback.
- UDP 3478: TURN/UDP.
- UDP 50000-60000: WebRTC ICE/UDP media range.

Возможна конфигурация UDP mux на одном порту, но переход на неё делаем
только осознанно и отражаем в документации и firewall.

Проверяемая цепочка transport fallback:

Direct WebRTC UDP
        -> TURN/UDP
        -> WebRTC TCP
        -> TURN/TLS over TCP 443

[ ] Смоделировать блокировку UDP.
[ ] Проверить TCP fallback.
[ ] Проверить TURN/TLS через TCP 443.
[ ] Убедиться, что тестовый клиент действительно использовал ожидаемый

Критерий завершения этапа:
